    How it works

    取得、抽出、整形、配信までを自動で実行します

    1. 取得技術系メディアと公式ブログ8サイトのRSSを取得します。
    2. 抽出AI関連のキーワードを含む記事だけを残し、広告表記の記事と配信済みの記事を除きます。
    3. 整形媒体名、タイトル、公開日時、RSSの概要文、URLを、読みやすい文面にまとめます。
    4. 配信Slackに投稿します。該当記事が0件のサイトも「0件」と知らせます。決まった時刻にGitHub Actionsが自動で起動し、配信は7時台と17時台です。

    要件定義

    概要

    開発プロセス要件定義 → 基本設計 → 実装 → 単体テスト → ドライラン → 本番確認。各工程の成果物を生成AIにレビューさせ、指摘は公式情報やテストで裏付けてから取捨選択しました
    技術Python 3.12、GitHub Actions、feedparser、requests、PyYAML、pytest、Slack Incoming Webhook
    運用費用0円(GitHub Actionsの無料枠のみ。常時稼働サーバーなし)

    目的・基本方針

    • 目的:技術系メディアからAI関連ニュースを自動で集め、重複を除いてSlackへ定期配信し、情報収集の手間を減らす。
    • コスト:初期費用・運用費用ともに0円。常時稼働サーバーの保守を不要にする。
    • 対象メディア:ITmedia AI+、TechCrunch(AIカテゴリ)、BRIDGE、Publickey、OpenAI News、Hugging Face Blog、gihyo.jp、IEEE Spectrum(AIトピック)。

    コンテンツ利用の考え方

    • 取得元は各メディア公式のRSS/Atomのみ。記事ページのHTMLは取得しない。
    • 表示するのは、RSSで提供されたタイトルと概要文だけ。概要文は表示のためにHTMLタグと余分な空白を除くだけで、要約・翻訳・切り詰めはしない。
    • すべての記事にメディア名と元記事へのリンクを付ける。
    • RSSの利用条件でよく求められる「提供内容のみ表示、改変しない、発信元とリンクを示す」に沿うための設計。利用条件は変わることがあるので、運用前に各メディアの最新の条件を確認する。
    • 設定ファイルに記載したサイトだけを対象にし、運営者から中止の要請があれば該当サイトを削除して直ちに止める。

    機能要件

    区分仕様
    収集実行時刻から過去24時間以内に公開された記事。日時はJSTに統一し、公開日時のない記事は対象外
    抽出タイトルと概要文に日英のAI関連キーワード(AI、生成AI、LLM、OpenAI、generative AI など12語)を1つ以上含む記事。AI専門カテゴリや公式ブログのフィードは、サイト単位でキーワード判定を省略できる
    除外タイトルに【PR】などの広告表記、タイアップ、広告、ウェビナー、Sponsored などを含む記事(単体の「PR」はプルリクエストと区別できないため対象外)
    重複排除計測用パラメータを除いた正規化URLで判定。通知履歴をJSONで直近7日分保持
    件数1サイト1回あたり新しい順に最大10件。超えたサイトは件数を付記し、24時間以内なら次回以降に配信
    配信サイトごとに1通。上限を超えたら分割。表示はメディア名・タイトル(リンク)・公開日時・RSS概要文。リンクプレビューは無効。各回の先頭にサイト別件数の見出し、末尾に区切りを投稿
    0件時0件・取得失敗のサイトもそれぞれ1通で知らせる(「新着なし」と「止まっている」を毎回見分けられるようにするため)。全サイトの取得に失敗した場合はニュース側には通知せず、警告のみ
    スケジュール毎日 06:15 / 16:15(JST)予定。GitHubの定期実行は約1時間遅れるため前倒しし、配信は7時台・17時台。手動実行は「本番」「ドライラン(送信・履歴更新なし、ログのみ)」「警告チャンネルのテスト送信」を選べる

    非機能要件

    区分仕様
    アクセス配慮1リクエストごとに2秒待機、タイムアウト10秒。User-Agentにボット名と連絡先URLを明記
    リトライ通信エラー・5xxは3秒間隔で最大3回。4xxはリトライしない。Slackは429もリトライ
    フェイルソフト1サイトが失敗しても残りのサイトを処理して配信する
    失敗時の順序送信できた分の履歴を保存 → 警告チャンネルへ送信 → ジョブを異常終了(GitHubのメール通知で検知)
    監視サイト別の取得件数と処理経過をログ出力。取得失敗・送信失敗・全サイト失敗を警告チャンネルへ通知
    同時実行制御定期実行と手動実行が重なっても履歴が競合しないよう直列化
    保守性サイト・キーワード・上限・待機秒数などは設定ファイルに外出し。コードを変えずに運用を変えられる
    セキュリティWebhook URL 2件は GitHub Actions の Secrets で管理し、コードやログに出さない。ワークフローの権限は contents: write のみ
    Design

    基本設計

    GitHub Actionsのジョブが1回で収集から配信までを行い、状態(通知履歴)はリポジトリ内のJSONファイルだけで持ちます。外部DBや常駐プロセスは使わず、依存ライブラリとActionsはバージョンを固定しています。

    構成

    GitHub Actions(cron / 手動)
  → RSS取得(8サイト)→ 絞り込み・重複排除 → Slack送信(ニュース / 警告)
  → data/history.json を更新して commit・push

    モジュール

    ファイル責務
    main.py実行モードの受け取り、パイプライン制御、終了コード
    config.py設定ファイルと Secrets の読み込み・入力チェック
    http_client.py待機・タイムアウト・User-Agent・リトライの共通処理
    fetcher.pyRSS取得・解析、JST変換、HTMLタグ除去
    filters.py / url_utils.py時間・キーワード・除外の判定、URL正規化
    history.py履歴の読み書き・重複判定・7日ローテーション
    notifier.pySlackメッセージの組み立て(開始見出し・サイト別・0件/取得失敗・終了区切り)・エスケープ・分割・送信

    設定ファイル(settings.yaml の抽粋)

    sites:
  - {name: ITmedia, feed_url: "https://rss.itmedia.co.jp/rss/2.0/aiplus.xml", summarize: false}
  # ほか7サイトも同様。AI専門のフィードは keyword_filter: false
keywords:
  include: [AI, 生成AI, LLM, OpenAI, generative AI, ...]
  exclude_title: [【PR】, "[PR]", "PR:", タイアップ, 広告, ウェビナー, Sponsored, ...]
limits: {window_hours: 24, max_per_site: 10, history_days: 7}
http: {wait_sec: 2, timeout_sec: 10, retry_count: 3, retry_interval_sec: 3}
slack: {wait_sec: 2, max_blocks_per_message: 45}

    処理フロー

    1. 設定・Secrets・履歴を読み込む(失敗したらその場で異常終了)。
    2. サイトごとにRSSを取得。失敗したサイトは記録して次へ。
    3. 時間 → キーワード → 除外 → 重複排除の順に絞り込む。
    4. サイトごとに新しい順に並べ、各サイト先頭10件を残す。
    5. 開始見出し → サイトごとの投稿(0件・取得失敗も1通)→ 終了区切りの順に送信し、送信できた1通に載せた記事だけを履歴に確定する。
    6. 履歴を保存し、必要なら警告を送り、送信失敗があれば異常終了する。

    ワークフロー

    • 定期実行は cron をUTCで指定し、実績で約1時間遅れるため、目標時刻の約1時間前(06:15 / 16:15 JST)に設定する。
    • 定期実行では手動実行用の入力が空になるため、モードはワークフロー側の式で確定させてからPythonへ渡す。
    • 履歴の commit・push は、Pythonが異常終了しても必ず実行する(送信できた分を失わないため)。
    • 別に、push ごとに単体テストを実行するワークフローを用意。
    Quality

    設計上の工夫とテスト

    動かして見つかった問題と、その対処をまとめています。

    課題工夫
    「生成AIの」のAIが一致しない、emailのaiに誤って一致する正規表現の \b は日本語も単語の文字とみなすため使わず、「前後にアルファベットが続かない」という前後判定で記述。全角・半角はNFKCで吸収
    送信失敗した記事が「通知済み」になり、二度と届かない送信できた1通に載せた記事だけを履歴に確定。分割送信の途中で失敗しても、未送信分は次回再送される
    履歴ローテーション後に同じ記事が再通知される公開日時のない記事を対象外にし、「常に24時間以内」と判定される記事を生まない
    タイトルの & < > でSlackのリンクが壊れる値ごとにエスケープしてからリンク形式に組み立てる
    Slack自体が落ちていると警告も届かない送信失敗時はジョブを異常終了させ、GitHubのメール通知で検知する
    全サイト障害時に「該当なし」と誤報する「新着なし(正常)」と「取得全滅(異常)」を区別し、後者は警告のみ
    本番を汚さずに動作確認したいドライランモード(送信・履歴更新なし、送信内容をログ出力)を手動実行の既定にする
    ライブラリ更新で突然壊れる依存ライブラリとActionsのバージョンを固定
    1サイトの新着が多いと、件数上限を1サイトが占有する上限を全体ではなくサイトごとに設定(各10件)。あふれた記事は履歴に入れず、24時間以内なら次回に配信
    AI専門カテゴリの記事が、タイトルにキーワードを含まず漏れるサイト単位でキーワード判定を省略できる設定(keyword_filter)を追加。広告の除外語は引き続き適用
    除外語「PR」が「GitHubのPR修正」(プルリクエスト)に誤一致する除外語を【PR】・[PR]・PR: などの広告表記の形に限定し、テストで両方を確認
    GitHubの定期実行が約1時間遅れる実績の遅れを測り、目標より約1時間早い時刻に設定
    連続投稿で、どこから今回分か分からない各回の先頭に件数一覧の見出し、末尾に区切りを投稿
    警告チャンネルが本当に届くか、障害が起きるまで分からない警告チャンネルへテスト通知だけを送る手動モードを用意し、到達を確認

    テスト

    pytest で単体テスト64件(拡張モジュールのテストを含む)。外部通信はすべて差し替え、次を確認しています。

    • キーワードの一致・不一致(「生成AIの」「全角ＡＩ」「email」「PRESS」など)、広告表記「【PR】」とプルリクエストの「PR」の区別、24時間の境界
    • URL正規化、履歴のローテーションと壊れたファイルの検出
    • エスケープの順序、分割、省略件数の付記位置、Slack送信のリトライ
    • パイプライン全体:送信失敗時の履歴、分割途中の失敗、全サイト失敗、ドライラン、Secretsの不足、サイトごとの上限と超過表示、0件・取得失敗の通知、開始見出しと終了区切り、警告チャンネルのテスト送信

    拡張と今後の改善

    AI要約モジュール(実装済み・既定では無効)

    サイトごとの summarize を true にすると、記事本文を取得して生成AI(Gemini API)で日本語に要約する構成を実装しています。公開版では、記事の利用条件に配慮して全サイト false(無効)を既定とします。有効にする場合は、対象サイトの利用規約が本文の自動取得と要約を許しているかを先に確認します。

    設計内容
    本文取得robots.txt をホストごとに確認。取得に失敗したらRSS概要文を要約元にする
    リトライ429/5xx は待機時間を倍々に伸ばして再試行。上限を超えたら代替モデルへ切り替え
    失敗時要約できなければ【RSS概要】ラベルでRSS概要文を配信し、記事が届かない事態を防ぐ
    品質120文字程度を指示し、上限を超えたら文末(「。」)で切る。記事中の指示文には従わないよう指示。モデルが付け足す「(121文字)」などの注記は除去
    追加のSecretsGemini APIキー(有効にする場合のみ必要)

    今後の改善候補

    • 別メディアが報じた同じニュースの重複を、タイトルの類似度でまとめる
    • AI専門カテゴリのフィードは、キーワード判定を省略できるようにする
    • 配信件数や失敗率を集計して、週次でレポートする
    デモの記事とタイトルはすべて架空のものです。
